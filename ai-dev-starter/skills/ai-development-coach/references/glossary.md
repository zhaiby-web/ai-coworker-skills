# 开发术语与回执句式速查（通用版）

给缺少研发背景、但需要指挥 AI 做开发的人。每个术语按三问结构：这是什么意思？能证明什么、不能证明什么？下一步该追问什么？

一句话原则：**开发回执里的术语不是结论，术语背后要看证据和边界。**

## 1. 工程流程类

| 术语 | 是什么 | 能证明 / 不能证明 |
|---|---|---|
| 门禁 | 进入下一阶段前必须通过的检查（单测、lint、构建、冒烟、验收） | 门禁通过=可进下一步；本地门禁通过 ≠ 正式验收通过 |
| commit | 本地改动形成一次可追踪的提交记录 | 代码有版本了；仍只在本机 |
| push | 本地提交推到远程仓库 | 团队能看到了；≠ 进入审查 |
| MR / PR | 合并请求，请团队 review 并决定是否合入 | MR 通过=团队同意合入；≠ 已上线 |
| dirty | 工作区有未提交改动 | 需确认哪些属于本任务，混杂提交是主要风险 |
| staged | 已加入本次准备提交的范围 | 会进入 commit，范围要逐文件确认 |
| untracked | 新文件还没被 Git 管理 | 「完成但还有 untracked」不算闭环，MR 会漏文件 |
| P0/P1/P2/P3 | 问题严重级别：阻断 / 阻塞验收 / 中等 / 加固建议 | 各团队标准不一，以项目规范为准 |

## 2. 环境与构建类

| 术语 | 是什么 | 关键不等式 |
|---|---|---|
| 环境分层 | 本地 → 测试/联调环境 → 集成环境 → 用户验收环境 → 生产 | 本地跑通 ≠ 测试环境跑通 ≠ 可发生产 |
| 标准入口 | 团队约定的统一页面访问方式 | 非标准入口的测试结果可能不被认可 |
| bundle | 前端源码构建后浏览器真正加载的资源包 | 加载到旧 bundle = 你测的是旧代码 |
| manifest | 资源清单，告诉浏览器加载哪个 bundle | manifest 指向不存在的文件 → 页面空白/加载失败 |
| `200` | HTTP 成功状态码 | 资源可访问；≠ 内容正确、≠ 功能成功 |
| 生产构建 | 把代码按正式流程打包 | 构建通过 ≠ 业务验收通过 |

## 3. 测试与验收类

| 术语 | 是什么 | 能证明 / 不能证明 |
|---|---|---|
| 单测 | 验证某个函数/模块局部正确 | 局部正确性证据；不是真实页面完整验收 |
| lint | 代码规范检查 | 规范无报错；≠ 业务功能正确 |
| 冒烟（smoke） | 只验主链路能不能跑通的快速测试 | 主链路没冒烟；≠ 全量验收通过 |
| 红灯证据 | 先让测试真实失败、拿到失败日志再修 | 防止没证据就改代码的严谨做法 |
| 定向测试 | 只跑指定测试文件 | 「定向参数被脚手架拒绝」= 项目命令不支持，只能跑全量 |
| HAR | 浏览器网络请求记录文件 | 可证明请求收发；默认含 cookie/token，必须脱敏 |

## 4. 页面与接口类

| 术语 | 是什么 | 你怎么理解 |
|---|---|---|
| DOM | 浏览器眼里的页面结构树 | 看得见的按钮在 DOM 里都有对应元素，但不一定有稳定标识 |
| selector | 在 DOM 里找元素的地址线索 | 定位失败常是线索失效，不是功能消失 |
| fallback | 理想动作做不到时的安全降级 | fallback 不是成功，是安全兜底；出现即应追查上游 |
| API | 系统之间传数据的通道 | 接口 |
| payload | 请求体 | payload 决定后端知道了什么 |
| response | 接口响应 | response 决定前端下一步展示什么 |
| 请求发出 | 网络面板里看到请求 | 只证明「问题送到了后端」，≠ 后续处理成功 |

## 5. 安全与脱敏类

- **脱敏**：隐藏 token、cookie、header、身份、单号、金额等敏感信息。原则：本机可看完整信息，但跨会话、回执、共享文档默认只传脱敏摘要。
- **只读白名单**：允许 AI「查一查」，不允许 AI「替用户动手办」。写操作、高风险动作默认禁止自动执行。
- **独立调试浏览器**：AI 调试工具只连专用的干净浏览器配置，不连日常浏览器（不登邮箱、不存密码、只登测试环境）。

## 6. 常见回执句式翻译

| 回执原句 | 人话翻译 | 该追问什么 |
|---|---|---|
| 「有条件通过，但不建议作为正式验收完成态合入」 | 部分检查过了，关键问题没闭环，不能当完成 | 哪些条件没过？阻塞合入或验收吗？ |
| 「lint 和格式检查均无输出错误」 | 规范层面干净 | 功能验证呢？这只是低级错误检查 |
| 「资源清单指向的文件在服务上不存在」 | 浏览器被指去拿一个不存在的文件 | 页面是不是空白/加载了旧代码？ |
| 「请求已发出，但界面走了兜底」 | 问题送到了后端，前端没能完成理想展示 | 断点在响应内容还是前端执行？ |
| 「证据口径收拢」 | 重新界定证据到底能证明什么，防止过度推断 | 收拢后还剩什么是确认的？ |
| 「没看到 X 的诊断信息」 | 缺这一项的证据 | 注意：这 ≠ 「X 结果为零」，只是没拿到证据 |
| 「构建产物已更新并可访问」 | 新代码打包好了、浏览器拿得到 | 页面实际加载的是新版吗？ |

## 7. 收到复杂回执的固定八问

```text
1. 这次到底验证了哪个目标场景？
2. 是否真的进到了目标页面/数据/操作？
3. 请求发出了吗？响应回来了吗？
4. 失败发生在哪一层（入口/前端/运行时/后端/数据）？
5. 当前证据能证明什么？不能证明什么？
6. 有没有未脱敏的敏感数据风险？
7. 是否阻塞合入、验收、联调或发布？
8. 下一步应该由谁处理？
```

## 8. 最重要的判断框架：事实 / 判断 / 动作

```text
事实：工具实际看到了什么？
判断：执行人基于事实推断了什么？
动作：下一步要谁做什么？
```

- 只有判断没有事实 → 追问证据。
- 有事实但判断跳太远 → 收拢证据口径。
- 有下一步但没有责任人 → 让派工方点名。

一句话小抄：**看懂开发回执，不是背术语，而是把术语翻译成：证据、风险、下一步。**
